(rain, sky), and the billboard effect task. Evidence: disassembly/decompile of the cited functions and the capture
`build\scene_capture_actors.txt` (stage-1 attract demo, frames 2780–3299; K/T/Z/N/M/E lines).

## 1. CRT rand

- `CRT_rand` 0x004ADED2: `holdrand = holdrand*214013 + 2531011; return (holdrand>>16) & 0x7FFF`, holdrand at
  per-thread data +0x14 (`_getptd` 0x004B02A1), initial value 1 (MT CRT default). CONFIRMED (chain test).
- All 538 game call sites call the thunk `jmp` 0x004ABE60 (none call 0x004ADED2 directly; no pointer references).
  The capture's return addresses are therefore the call sites + 5.
- `CRT_srand` 0x004ADEC5 has one caller, the wrapper 0x004ABE70, whose only caller is **`Game_SeedRandom` 0x004157D0**:
  `srand(Game_IsDemoMode() ? 0 : *(u32*)0x009A32A0)`; `Game_IsDemoMode` 0x00413280 = mode 0x009C8E98 ∈ {5, 9, 10, 11}
  or (6 and 0x009C90A4 == 8). Callers of Game_SeedRandom:
  - `Stage_Start` 0x00460030 (clears 0x009A26A4 first) — demo frame 2786;
  - event op **0x4D** 0x0045EEC0 (stage/camera reset): always, except in mode 5 where only the first 0x4D after a
    stage start reseeds (flag 0x009A26A4) — demo frame 2788.
  - So the attract demo is always seed 0. CONFIRMED: Z(2786) = 150 steps from 0, Z(2788) = 67 steps from 0.
  - Outside demo modes the seed is 0x009A32A0 (HYPOTHESIS: a global frame counter, writers 0x0049F4AA / 0x0040AA02),
    i.e. it depends on when the player starts; a port wanting identical gameplay must reproduce that counter.

### Order inside a frame

`Task_Run` 0x004A71A0 is recursive: for a task it runs its `+0x28` child list, then its own function (under setjmp),
then its `+0x24` list. `Task_Create` 0x004A6FA0 appends the new task to the **end of the current task's parent's
+0x28 list** (root 0x007DF878 when called outside a task). In the demo every task is a root child, so execution
order = the K-line order, and a task created during the frame runs later in the same frame. With the demo's tree:

1. event VM (65574): op 0x4D → srand(0); ops 0x1B/0x1C/0x1D (sky type/mode, rain flag); spawn ops 0x09/0x0B append
   enemy/prop tasks (their rand calls happen when they first run, i.e. at the end of the frame);
2. sky (65577, no rand); 3. player 1 then player 2 (65579/65580 `Player_Task` 0x00413E90 → Player_DemoInput:
   1 + 2·shot calls each); 4. rain (65585): 3 per respawn; 5. everything later in the list: props, enemies
   (motion variants, target choice, hit reactions), one-shot tasks, billboard effects (type 0x53 only).

CONFIRMED by the replay test: seeding as above, running the ported player and rain consumers in this order and
skipping the remaining counts reproduces Z on all 520 frames, and the rain/shot decisions (which depend on the
exact values) match. The order *among* step-5 consumers is not checked (only their sum); it follows the K order.

**Spec for the port:** keep one `game::CrtRand` (state 1 at boot); seed 0 at stage start and at op 0x4D (demo
modes); run tasks in creation order with the append rule above; every ported consumer must draw exactly its calls
(list above / CSV). Not yet ported: enemies, props, hit sounds — until they are, the stream diverges at the first
enemy decision (frame 2881 in the demo), after which the rain differs too.

## 2. Rain — Rain_Init 0x004138A0, Rain_Task 0x004136A0 (CONFIRMED)

- Created by `Stage_InitTasks` 0x00460710 (task fn 0x004136A0, 0x58 bytes). Pool 0x007C1EB8: 50 × {x, y, z} floats in
  camera-yaw space. Init: x = rand%20 − 10, y = rand%50 − 25, z = rand%25 − 35 (this order). Clears the flag 0x009C8E50.
- Runs only while 0x009C8E50 == 1 (event op 0x1D; set at 2788 in the demo). Per particle, in pool order:
  `y = y − 2`; if `y <= −7`: x, y, z re-rolled as at init (no decrement after a respawn).
  Position: `w = (x, y, z)·Ry(camera yaw) + camera pos` (context 0x009C6F00: yaw +0xD0, pos +0xC0; pitch is ignored,
  so the streaks stay vertical). Facing: `yaw' = Cam_DirToAngles(w.x − cam.x, 0, w.z − cam.z)`.
  Matrix: `S(1.5, 3.5, 1) · Rz(0x100) · Ry(yaw') · T(w)` (then ·V), model 0x53 (stage1.bin streak), drawn through
  0x004185A0 → 0x004AA350 with 0.5 in draw-record word 4, draw flags 0xE (0x004A79F0) during the loop, 8 after.
- Lifetime: a particle spawned at y lives ceil((y+7)/2) frames; ≈ 9 respawns per frame (4,658 over 512 frames).
- Not modelled: what record word 4 = 0.5 and draw flags 0xE mean for the renderer (alpha/sort? — renderer agent).

## 3. Sky — Sky_Task 0x004132D0, Sky_Create 0x004134D0

Table 0x00579968 (16 bytes per type: s16 model, s16 model2, f32 yOffset, s32 yawStep, s32 yawInit), e.g. type 0
{6048, 6911, 0, 12, 0}, type 4 {6048, 6911, 0, 4, 0}. Per frame:
`if type != prevType: yaw = yawInit`; mode 0 → nothing drawn; types 8/10/11 → screen-fixed panels (0x00413620 /
0x00413500, not ported); otherwise `if mode != 2: yaw += yawStep`, model drawn with
`S(1.2, 1.2, −1.2) · Ry(yaw) · T(cam.x, cam.y + yOffset, cam.z)` (type 5: `S · Ry(−yaw) · Rz(0x8000) · T`) and model2
with `T(...)` only. Type and mode come from event ops 0x1B / 0x1C.

- **Stage-1 demo (CONFIRMED, 1,024 draws):** op 0x1B sets type 4 at 2788, so `yaw = 4·(frame − 2787)` (4 at the first
  stage frame). Note the **negative z scale** (−1.2) — the fitted `scale 1.2` is uniform; mirror-handedness matters
  for culling. The scene files' `yaw 4322 yaw_per_frame 4` is wrong for the stage (base must be 0 at frame 2787).
- **Title (HYPOTHESIS, strong):** the title never sets a type: `Sky_Create` sets type = prevType = 0, so the yaw is
  never reset and starts from **uninitialised task memory** (+0x48 is outside the 0x34 bytes `Task_Create` clears).
  Type 0 steps **12 per frame**, not 4: the observed title yaw (run1 capture, frames 608–1086, view from the C lines)
  advances 12.02/frame on average but in plateaus and jumps of exactly 1/512 rad (20.37 units). That is what `Mtx_RotY`
  does with a huge yaw: `fild; fmul K (double); fstp float` quantizes the angle to float precision at 2¹⁴–2¹⁵ rad.
  A model `angle = float(Y0 + 12·(f − 608)) · K` with a single float rounding fits all 479 title frames (max error
  2.0e-4 rad, mean 3.8e-5; the best unquantized 12/frame line has max error 1.07e-3). Y0 is not unique
  (14 candidates in 1.8e8–3.4e8, e.g. 180,687,068) and depends on the heap's earlier contents. For the port:
  `yaw = Y0 + 12·(frame − 608)` with Y0 = 180687068 and the float rounding reproduces the run-1 title.

## 4. Billboard effects — Eff_Spawn 0x004073B0, Eff_Task 0x00407A70 (CONFIRMED for types 0x61/0x62)

- Spawn block (floats): pos[3], pitch, yaw, ?, scale[3] (−1 = default), type (low byte), faceMode, ?.
  Wrappers: `Eff_SpawnAt` 0x00407340 (pos+angles pointer, type, faceMode, arg; scale −1; 40 callers),
  `Eff_SpawnBlock` 0x004073A0. faceMode ≠ 0 → `Cam_DirToAngles(cam − pos)` gives pitch/yaw (faceMode 2: pitch 0) —
  frozen at spawn, not re-billboarded per frame.
- Type switch → models first..last (+0x60/+0x64), base scale, roll: see `game::EffectDefinition` (e.g. 0x61/0x62
  0x1339–0x1356 at 1.0/1.5; 0x53 0x125–0x13D with roll = rand()%0xFFFF — the only rand in effects; 0x5A–0x5C roll
  0xC000; 0x5A also spawns 0x5C and 0x5D after itself; unknown types 0x904 at 0.1).
- Distance rule (only when scale is −1): z = view-space depth of pos (active context view): type 0x53: if z > −35:
  `scale = |max(z, −0.001)·(−1/35)|`; type 0x63: none; others: if z > −15: `scale = max(z·−0.0667, 0.25)`. Then
  scale y = z = x. In the demo all effects were farther (z ≈ −27…−33), so the table scale is kept (CONFIRMED values).
- `Eff_SpawnScaled` 0x00407BC0 (types 0x5A–0x5D, always faces the camera; z > −30: `scale = max(z·−1/30·scale, 0.25)`).
- Task per frame: `S(scale·(0.75 if type 'S' and model < 0x129)) · Rz(roll) · Rx(pitch) · Ry(yaw) · T(pos)`, light
  colour for 'P' (1, 0.3, 0) and 'S' (0.85, 0.85, 0.75) via Light_SetColor 0x004AA0A0, draw model +0x60, then
  `+0x60++`; dies when +0x60 > +0x64 or flags +0x5D & 2. So an effect lives last − first + 1 frames (30 for
  0x1339–0x1356), drawn first in its creation frame. `Eff_PlaySound` 0x00407950 is called after the spawn.
- Demo instances: 65604 type 0x62 from the one-shot task 0x00433AC0 (frame 2830), 65606/65608 type 0x61 from enemy
  code (frames 2940, 3023). Model range 0x1339–0x1356 is presumably a water splash (HYPOTHESIS; stage 1 has water).

## 5. Correction: 0x00413E90 is the player task

Tasks 65579/65580 (fn 0x00413E90) are **per-player** tasks (task +0x34 = player index; records 0x009A5C60 + i·0x130,
0x009C8FC0 + i·0x14), not a stage effect. They run the demo input (above) and draw the shot flash: models
373–381 + 2934–2942 (P1) and 383–391 + 2948–2956 (P2), each a 9-model sequence at view depth 1 per shot (17 / 24 shots),
plus models 2936 / 2950 at world positions (788 / 1036 draws; bullet streaks? HYPOTHESIS). Not ported (player subsystem).

## 6. Port

- `src/game/rng.{h,cpp}`: `CrtRand` (exact, `Advance` in O(log n)), `GameIsDemoMode`, `GameRandomSeed`,
  `PlayerDemoInput` (0x00415710).
- `src/game/effects.{h,cpp}`: `Rain` (Init/Update/World), `LoadSkyTable` + `Sky::Update`, `EffectDefinition`,
  `BillboardEffect::Spawn/SpawnScaled/Step`, `EffectSound`. World matrices exclude V.
- `tests/effects_test.cpp`: `build\Release\effects_test.exe game build\scene_capture_actors.txt` (checks in the table
  at the top; event ops are taken from the capture's E lines). `tools/rand_sites.py` regenerates the call-site CSV.
